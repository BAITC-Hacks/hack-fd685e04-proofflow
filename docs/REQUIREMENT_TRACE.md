# ProofFlow: приемка по кейсу Электрокомплект

Источник: предоставленное команде ТЗ «Автоматический расчёт заказов поставщикам
для пополнения склада» (трек 05, задание 01). Эта матрица не заменяет ТЗ и
не обещает балл жюри. Статусы ниже — результат независимой проверки дерева
репозитория **23.09.2026 около 15:16 UTC+5**; после изменений их следует
перепроверить. Отсутствие теста не означает работоспособность, а зелёный
тест на синтетике не доказывает качество на реальных данных.

| Требование ТЗ | Текущая реализация и доказательство | Статус / остаётся проверить |
| --- | --- | --- |
| Must have 1: история продаж, остатки, товары в пути, категории, рост влияют на количество по артикулу | `engine.calculate`; направленный `tests/test_acceptance.py::test_every_quantitative_must_have_input_changes_a_recommendation` меняет каждый численный источник отдельно; `tests/test_engine.py` проверяет датированный приход | **Синтетика подтверждена.** Реальную загрузку отчётов партнёра и точность остатков/ETA требуется проверить отдельно. Категория влияет через настраиваемые `growth`/`safety_days`, а не через скрытую эвристику. |
| Must have 2: сезонность и устойчивый рост | Дневной/месячный коэффициенты и тренд в `engine.py`; `tests/test_engine.py::test_seasonality_is_non_neutral_and_future_date_specific`, `test_isolated_client_order_spike_removed_but_sustained_growth_retained` | **Синтетика подтверждена.** На месячных выгрузках нельзя заявлять наблюдаемую дневную сезонность. Нужна валидация на данных партнёра, если структура достаточна. |
| Must have 3: упущенный спрос во время отсутствия товара | Явные интервалы `stockouts`; `tests/test_engine.py::test_explicit_stockout_imputes_lost_demand_and_raises_recommendation` | **Синтетика подтверждена.** Нельзя утверждать компенсацию по реальному архиву, пока в нём не найдены даты stockout; не выводить их из нулевых продаж без проверки. |
| Must have 4: исключение разового крупного заказа, включая одного клиента | Порог + концентрация на обезличенном клиенте или событии; `tests/test_engine.py::test_isolated_client_order_spike_removed_but_sustained_growth_retained`, `test_event_id_can_flag_one_off_order_without_claiming_customer_identity` | **Синтетика подтверждена.** `event_id` документа не является клиентом. Для полноценной проверки именно одного клиента необходим обезличенный клиентский ID в источнике. |
| Must have 5: список по поставщикам с объяснением каждой позиции | `supplier_groups`, `rows[].explanation`, `breakdown`; `tests/test_acceptance.py::test_same_sku_isolated_by_warehouse_and_grouped_by_supplier`, `tests/test_engine.py::test_supplier_groups_and_explanations_match_real_calculation` | **API/ядро подтверждены.** Проверить финальный UI и поведение при отсутствующем поставщике: ядро относит его к `UNASSIGNED`, но HTTP слой пересобирает группу с пустым ключом. |
| Сценарий менеджера: склад/категория → список → проверить/исправить → утвердить | Фильтры и endpoints в `server.py`, SQLite approval в `storage.py`; `tests/test_end_to_end.py` проверяет цикл demo–calculate–detail–approve–export | **API частично подтверждён; UI ещё не подтверждён визуально.** Нужна проверка после завершения фронтенда; утверждение не должно маскировать черновик. |
| Выход: артикул, поставщик, количество, причина, срочность, экспорт | `engine.py`, `exports.py`; `tests/test_acceptance.py::test_export_is_a_flat_reviewable_csv_and_xlsx_not_a_sent_order` | **CSV/XLSX структура подтверждена на синтетике.** Точная схема импорта в 1С партнёра не предоставлена, следовательно совместимость с их учётной системой **не проверена**. Нужен образец/подтверждение партнёра; до тех пор это универсальный ручной экспорт. |
| Приватность и обезличивание клиентов | Локальный bind, некоммитируемое хранилище, отказ от отправки поставщикам; `tests/test_api.py` проверяет Origin и отправку | **Открытый риск:** прямой `POST /api/calculate` принимает произвольный `client_id`, а детали исключённого события могут вернуть его значение. Импортёр должен псевдонимизировать вход, но этого недостаточно без защиты прямого JSON API. Не вводить реальные ФИО/email до устранения риска. |
| Не отправлять заказ без подтверждения | В коде нет отправки поставщикам; экспорт черновика помечен, после approval отдельный файл; `tests/test_api.py` и `tests/test_acceptance.py` | **Подтверждено в текущем коде.** Сам экспорт по-прежнему ручная операция сотрудника, не автосенд. |
| Устойчивость к аномалиям, плохим входным данным | Явная валидация отрицательных/нечисловых объёмов, дат и дубликатов; отчёт об исключённом объёме в разборе | **Частично.** Стресс на реальной форме/объёме и zip/xlsx ещё не завершён; устойчивость не доказывается только примером выброса. |
| README: методология, выбросы, запуск | `README.md`, `docs/METHODOLOGY.md`, `requirements.lock`, `scripts/preflight.py` | **Текст имеется, чистый запуск не подтверждён этим аудитом.** README ссылается на `docs/DATA_MAPPING.md`, который на момент аудита ещё не был создан. Проверить путь и команду после слияния работы агента импорта. |
| Репозиторий и сдача на платформе | Код ведётся в официальном team repo; `docs/SPRINT.md` фиксирует два часовых инкремента | **Не финализировано.** Коммит/push не заменяет нажатие «Сдать решение». Проверить репозиторий, README, ссылку и форму платформы до freeze. |

## Минимальная финальная приемка

1. `python scripts/preflight.py` на чистой установке, затем отдельный запуск UI.
2. Реальный импорт обоих архивов партнёра и агрегированный отчёт о распознанных
   полях, потерянных строках и явно отсутствующих источниках (без публикации
   клиентских строк или самих файлов).
3. Изменить в UI каждый источник из Must have 1; продемонстрировать три
   диагностических примера: сезонность, stockout, разовый заказ.
4. Проверить ручную коррекцию количества, авторство утверждения, скачивание
   CSV/XLSX и невозможность автоматической отправки поставщику.
5. Подтвердить ограничения 1С и пропущенных входных полей в README/демо;
   не обещать интеграцию, которую не проверяли с владельцем задачи.
6. Подтвердить push в официальный репозиторий и отдельную сдачу через платформу.
