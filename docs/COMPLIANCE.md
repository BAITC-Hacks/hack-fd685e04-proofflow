# Проверяемое соответствие задаче и регламенту

Источник приоритета: актуальное объявление организатора → ТЗ выбранной задачи
Электрокомплекта → предоставленная редакция Положения → внутренние документы.
Этот файл — самопроверка команды, не решение жюри и не обещание оценки.

| Требование | Реализация / способ проверки | Граница доказательства |
| --- | --- | --- |
| История, остаток, товары в пути, категория, прирост | Канонический контракт `docs/CONTRACT.md`, `engine.py`, тесты изменения входов. | В исходных файлах часть полей отсутствует или требует подтверждения. Нулевой либо неизвестный остаток не заявляется измеренным. |
| Сезонность и устойчивый рост | Детерминированные факторы в `engine.py`, методика в `docs/METHODOLOGY.md`, тесты на сезонный/растущий ряд. | Короткая или искажённая история снижает достоверность прогноза. |
| Потерянный спрос при stockout | Компенсация при явных интервалах отсутствия товара; синтетический контрольный пример. | Партнёрские материалы не содержат точных stockout-интервалов. Нельзя утверждать, что по ним восстановлены реальные потерянные продажи. |
| Разовые крупные продажи и один клиент | Робастная обработка событий и клиентского ID при наличии анонимного ключа; тесты на всплеск. | Номер документа в материалах партнёра — не идентификатор клиента. Клиентскую повторяемость по этим файлам проверить нельзя. |
| Заказы по поставщикам с обоснованием | `engine.py` + API + интерфейс; рекомендуемое количество, срочность и объяснение для каждой позиции. | Выгрузка — пилотный CSV/XLSX, не подтверждённая схема документа 1С. |
| Проверка, корректировка и утверждение сотрудником | API и интерфейс позволяют менять количество и явно утверждать. | Автоматической отправки поставщику нет. |
| Анонимность и приватность | Локальное хранение, обезличивание идентификаторов на границе импорта/API, исключение исходных файлов из Git, localhost по умолчанию. | Однопользовательский пилот не имеет промышленной системы доступа/удаления. |
| Самостоятельный запуск жюри | README, `requirements.lock`, синтетическое демо, `scripts/preflight.py`. | Docker — опция, не проверенная на конкурсной машине; личная подписка не нужна. |

## Регламент разработки и представления

- Основная функциональность создаётся в официальном репозитории команды в
  соревновательное время. Код готового TransClaim не переносится. При
  использовании сторонних библиотек соблюдаются права их авторов; список
  прямых зависимостей — в `requirements.txt`, закреплённые версии — в
  `requirements.lock`.
- По п. 5.4.8 предоставленной редакции нужен проверяемый промежуточный
  результат к концу каждого часа. Git-коммит с тестами служит доказательством,
  но не заменяет результата. История — в `docs/SPRINT.md`.
- По пп. 5.4.15–5.4.16 и 5.6.6 самостоятельный запуск по README и работа
  ключевой функции без личной подписки участника критичны. Синтетический
  пример и локальный расчёт доступны без ключей.
- Финальный push не заменяет отдельную сдачу на платформе организатора до
  фактического freeze. Время и техническую форму сдачи проверяет капитан.
- Технические критерии задаёт конкретное ТЗ. Не применяем неподтверждённую
  универсальную шкалу и не обещаем 100 баллов; результат определяет жюри.

## Что нужно подтвердить для промышленного пилота

Дата/смысл снимка свободного остатка, способ учёта возвратов, интервалы
stockout, анонимный ключ клиента, договорные сроки поставки и настоящий MOQ,
семантика плановых ETA, цены/валюта, поля и процедура обмена 1С. См.
[`PARTNER_AUDIT.md`](PARTNER_AUDIT.md) и
[`1C_COMPATIBILITY.md`](1C_COMPATIBILITY.md). До подтверждения этих полей
рекомендации остаются черновиками, которые проверяет менеджер.
